## 统一故障类型说明

本说明帮助 L1 提出根因假设、L2 检查假设、Meta 比较已审核结果，不替代本案例的遥测证据。Meta 最终综合时只复制已选类型，不借本说明重新诊断。

### 怎样使用

- 先比较本组件、同一操作在正常和异常窗口的表现，再判断哪个类型更能解释变化。一个类型有具体支持、仍有少量疑问时，可以提出假设；只有“服务慢了”或“报错了”时，不能任意选一个类型。
- 下文“支持线索”是值得检查的现象，不是出现一项就确诊，也不是必须凑齐的清单。把支持、反证和缺少观测分别说清楚；不要要求现有数据无法提供的直接注入证明。
- 类型名称按公开输出词表使用。可以同时调查多个独立故障，但不要把同一处不确定故障的几个备选类型都当成独立根因输出。异常大小、分支数量和模型自评分不能代替类型依据。
- 只使用本案例授权的正常、异常两组遥测。不得读取标签、注入记录、标准传播图或包含答案的清单；不按案例编号、目录顺序、特定服务名、类型频率或历史评分猜答案。本说明及来源文档不能用作 evidence_refs。
- 下文提到的线程、重启、重传、解析地址、响应正文等数据，只有在授权遥测实际包含时才能查询。先用 inspect_telemetry 确认表和字段；缺少时说明缺口，不新增抓包、访问集群或故障注入操作。来源链接供维护者核对，不增加 Agent 的外部访问权限。

### 读数据时先避免这些误判

- **单位与样本**：analyze_traces 的 duration_ms、mean_child_ms 等字段是毫秒；不要再把它们按纳秒转换。原始字段先核对单位。指标直方图的 sum/count 是均值，不是单次调用耗时；工具返回的转换值 P95 也不是直方图事件的第 95 百分位。计数器比较先确认累计或区间含义，并处理重置；不同窗口长度要比较速率。
- **同一次请求**：比较相同操作、调用方和被调用方，核对 trace/span 身份及重试。客户端时长减服务端时长还包含排队、连接建立、重试和埋点范围差异，不等于纯网络时延；跨主机时间戳还可能偏移。父 span 减全部子 span 时长会重复扣除并行区间，不能据此直接算自身耗时。
- **数据缺失**：没有 span、日志或指标，可能来自采样、过滤、覆盖不足或采集异常。结合调用方实际请求、同窗口其他组件及可用性观测再判断；不能单凭“没查到”确定停机或网络中断。
- **起点归属**：等待最久、最早打印错误的组件可能只是受影响方。沿同一请求检查等待和错误从哪里传来。网络或 HTTP 异常可能位于调用两端之间，不能凭调用方向固定归到某一端；拿不准时保留归属疑问，不擅自更换本链起点。
- **共同原因**：请求量、操作占比、共享主机和其他依赖都可能同时改变多个组件。先核对这些差异，不把同时异常直接写成故障传播。

## Pod 与容器

Pod 是 Kubernetes 中承载一组容器的运行单元。以下两个选项按公开评测词表区分，不能只按英文名称直译。

### `pod_failure` — Pod 或容器被终止

- **中文含义**：公开类型映射中的 PodKill、ContainerKill，表示 Pod 或容器被终止；控制器可能随后重建或重启。
- **支持线索**：实际遥测出现终止、重启或实例身份更换，伴随请求失败、服务记录中断后恢复。恢复与生命周期变化一起出现，比单独一个空窗口更有区分力。
- **容易混淆**：pod_unavailable、网络隔离、采集器故障，以及内存耗尽引起的重启。重启是结果，不一定是最初故障；已经观察到内存故障时要核对先后关系。
- **如何区分**：查看已有的终止/重启日志、实例标识和请求时间序列，核对恢复前后是否同一实例。窗口过短、没有恢复或没有生命周期字段，都不能单独排除本类型。

### `pod_unavailable` — Pod 持续不能正常提供服务

- **中文含义**：公开类型映射中的 PodFailure，表示 Pod 在一段时间内被置于不可用状态；不要求一定被删除或重启。
- **支持线索**：在仍有调用需求时，应用持续不能服务，并有就绪状态、可用副本或应用健康异常相互印证。
- **容易混淆**：pod_failure、网络隔离和数据采集缺失。可用副本为零可见于多种故障；某些故障下容器仍显示 Running，不能把该状态等同于业务健康。
- **如何区分**：结合应用请求、探针/就绪记录和生命周期变化，检查窗口内是否恢复。持续到窗口末尾只是线索，不能靠持续时长硬分两种类型；缺少区分证据时说明两者仍可能。

## 网络传输

TCP（传输控制协议）会重传、排序和去重；应用侧现象与底层数据包故障不是一一对应关系。

### `network_delay` — 网络传输延迟

- **中文含义**：数据在网络路径上的传递变慢。
- **支持线索**：同一调用路径的端到端等待增加，而对应服务端处理变化较小；若已有网络往返时延等观测同时变化，支持更强。
- **容易混淆**：http_slow、network_loss、带宽限制、客户端排队及服务端处理慢。固定延迟平台也可能来自超时设置或方法内等待。
- **如何区分**：按同一请求比较调用两侧耗时，检查已有重试、网络和排队记录，比较同一服务的其他路径。只有客户端/服务端耗时差时，不宣称已经量出了网络时延。

### `network_loss` — 网络丢包

- **中文含义**：部分发送的数据包未能到达接收端。
- **支持线索**：已有的丢包或重传计数增加，并与相应调用路径的重试、尾部时延或失败率上升一致。
- **容易混淆**：network_corrupt、network_partition、拥塞和应用主动重试。重传有多种原因；阶梯状等待或几次重试本身不足以证明丢包。
- **如何区分**：检查已有网络计数的区间变化、受影响方向和成功请求比例，并区分传输层重传与重新发起的业务请求。没有包级证据时保留与其他网络类型的疑问。

### `network_partition` — 网络隔离或不可达

- **中文含义**：指定节点或组件之间的一部分通信路径被切断，可以只影响一个方向或一组目标。
- **支持线索**：某路径持续大范围连接失败或超时，同时目标从其他路径仍能服务，支持路径问题而不是目标整体停机。
- **容易混淆**：pod_unavailable、DNS 解析失败、严重丢包和连接拒绝。没有目标端 span 不足以证明隔离。
- **如何区分**：核对同一目标的不同调用方、正反方向及解析结果，查看授权日志中连接失败发生的阶段。只有单一路径失败而无其他对照时，不声称已区分隔离和服务不可用。

### `network_corrupt` — 网络数据包损坏

- **中文含义**：传输中的数据包内容发生损坏，可能被校验机制丢弃并触发重传。
- **支持线索**：已有数据包校验或损坏记录，与同路径重传、连接错误相符。TCP 可能隐藏损坏，使应用只看到变慢或超时。
- **容易混淆**：network_loss、网络设备错误和 http_payload_modified。一般 errors 计数或重传增加，不专门代表包损坏。
- **如何区分**：核对现有网络错误字段的具体含义及其变化；若只剩超时/重传，无法可靠地区分丢包和损坏。应用正文异常要先排查应用层改写，不直接归为包损坏。

### `network_duplicate` — 网络数据包重复

- **中文含义**：网络路径额外复制了数据包。
- **支持线索**：已有包级重复观测，或明确说明为重复包的网络计数，并与受影响路径对应。
- **容易混淆**：网络乱序、丢包引发的重复确认，以及应用重试。TCP 重复确认（ACK）有多种成因；重复日志、重复 span、重复业务请求都不是包重复的直接证明。
- **如何区分**：区分原始包、重传包和新业务请求。没有授权的包级观测时，不用业务重复次数代替网络重复证据；TCP 去重也可能使应用没有明显重复执行。

### `network_bandwidth_limit` — 网络带宽受限

- **中文含义**：网络路径可传输的数据速率受到限制。
- **支持线索**：在有足够传输需求时，实际吞吐受到限制；较大请求或响应的传输时间增长更明显，而服务端处理未同幅增加。
- **容易混淆**：network_delay、丢包、服务处理能力不足和请求量下降。吞吐变低本身不能证明带宽限制。
- **如何区分**：在请求大小、方向和并发可比的条件下，对照字节速率与调用时长；只有已有遥测包含这些量时才计算。缺少大小或需求信息时，说明无法判断是否真正受带宽限制。

## HTTP 请求与响应

HTTP（超文本传输协议）类型关注请求/响应处理过程；HTTP 状态码与 trace 的通用错误状态需要分开读取。

### `http_aborted` — HTTP 请求或响应被中断

- **中文含义**：HTTP 交互在正常完成前被中止，可能发生在请求或响应阶段。
- **支持线索**：调用出现中途关闭、连接重置、响应未读完或取消，且相关服务处理与调用方失败能在同一请求中对应。
- **容易混淆**：进程退出、网络隔离、客户端超时取消、正常业务错误响应。收到完整的错误状态码不等于连接被中断。
- **如何区分**：查现有调用和错误日志，确认失败阶段、是否收到完整响应，以及服务端是否已完成处理。单个 reset 或取消记录仍要考虑网络及生命周期原因。

### `http_slow` — HTTP 交互被延迟

- **中文含义**：HTTP 请求或响应在处理路径上出现额外等待，不等于所有慢接口都属于此类型。
- **支持线索**：延迟集中在可识别的 HTTP 交互或阶段，应用内部对应处理相对稳定，其他路径对照支持该范围。
- **容易混淆**：network_delay、network_loss、客户端排队、jvm_method_latency。HTTP span 慢只能定位现象，不能直接区分上述机制。
- **如何区分**：比较同请求两侧、接口方法/路径、响应开始或完成阶段（若有），结合内部 span 和网络观测。只有端到端耗时增加时，不能断言延迟一定发生在 HTTP 层。

### `http_payload_modified` — HTTP 内容或请求目标被改写

- **中文含义**：公开词表覆盖响应正文替换/修改，也覆盖请求路径或 HTTP 方法被改写；并非只指响应正文。
- **支持线索**：同一请求两侧记录的路径、方法或内容出现无法由正常处理解释的不一致，伴随解析、校验或业务结果异常。
- **容易混淆**：合法路由重写、请求参数不同、业务数据变化、jvm_method_mutated 和包损坏。仅有解析错误或一次“未找到”响应不够。
- **如何区分**：匹配同一请求，核对两侧实际记录的路径/方法/内容及正常窗口同类行为。没有正文记录时不要编造正文变化；不能将不同请求的数据差异当成改写。

### `http_response_status_modified` — HTTP 响应状态码被改写

- **中文含义**：HTTP 响应状态码被替换，调用方看到的状态可能不同于应用原本产生的状态。
- **支持线索**：同一请求的服务端业务结果或响应日志与调用方记录的 HTTP 状态码不一致，且正常窗口没有这种差异。
- **容易混淆**：应用真实报错、网关生成错误、鉴权失败，以及 trace 状态标记规则不同。错误码集中出现也不直接证明被改写。
- **如何区分**：核对两侧 HTTP 状态码、业务错误来源及中间代理的现有记录；不把通用 span status 与 HTTP 状态码直接比较为“被篡改”。

## 资源与 Java 虚拟机

CPU 指处理器；JVM 是 Java Virtual Machine（Java 虚拟机）；GC 是 Garbage Collection（垃圾回收）。先从遥测确认运行时，不把非 Java 服务的普通异常套进 JVM 类型。

### `cpu_stress` — 处理器资源压力

- **中文含义**：容器或其运行环境的处理器资源被大量占用，影响应用运行。
- **支持线索**：处理器使用、限额节流或运行队列变化与处理延迟对应，并超过可比正常负载下的变化。
- **容易混淆**：请求量增长、jvm_thread_cpu_stress、垃圾回收以及重试引起的 CPU 增长。低 CPU 也不自动排除短时压力或限额影响。
- **如何区分**：查看已有 CPU 序列、资源限额、吞吐和重试，核对压力与异常先后；有进程/线程信息时定位消耗来源，不能只按一个高占用点定类。

### `jvm_thread_cpu_stress` — Java 进程内线程造成的处理器压力

- **中文含义**：Java 进程内的线程大量占用 CPU，影响同进程其他工作。
- **支持线索**：JVM 进程或线程 CPU 增长，若已有线程栈或采样能定位持续消耗点，区分力更强。
- **容易混淆**：cpu_stress、正常业务计算、垃圾回收压力。线程数增加不等于 CPU 压力；JVM 与容器 CPU 可以同时升高，不能要求容器 CPU 必须正常。
- **如何区分**：对照同一时间范围、单位和核数口径的进程/容器 CPU，并查看已有线程或 GC 记录。只有容器 CPU 数据时，通常不能确定压力来自 Java 线程。

### `mem_stress` — 容器或系统内存压力

- **中文含义**：内存占用挤压容器或系统可用资源，可能引起回收、分配失败或进程被终止。
- **支持线索**：可比负载下内存持续接近实际限制，伴随内存压力、分配失败或 OOM（内存不足）记录。
- **容易混淆**：jvm_heap_stress、正常缓存增长和文件缓存。文件系统占用是磁盘用量，不能直接当成内存压力。
- **如何区分**：核对已有工作集、常驻内存、限制和内存不足日志；Java 服务还要区分堆、堆外与其他进程。不能把缓慢增长或一次页错误直接当成故障。

### `jvm_heap_stress` — Java 运行时内存压力

- **中文含义**：Java 运行时内部内存承压，常见为堆空间紧张。公开映射归并 JVMMemoryStress，底层也支持栈压力；不要仅凭选项含 heap 就忽略实际异常部位。
- **支持线索**：堆使用逼近堆限制、回收后仍难以下降，或已有日志明确说明 Java 堆/栈分配问题。
- **容易混淆**：mem_stress、jvm_gc_pressure、业务内存增长、递归导致的栈溢出。OutOfMemoryError 也可能来自堆外或本地内存，不等于必然是堆耗尽。
- **如何区分**：查看异常的完整原因、已有堆使用/上限及回收前后变化；若是栈溢出，要检查已有方法栈中的递归线索。单凭异常名称不能证明人为内存压力。

### `jvm_gc_pressure` — Java 垃圾回收造成的运行压力

- **中文含义**：垃圾回收活动占用较多时间或造成停顿，影响应用处理。
- **支持线索**：GC 次数、耗时或停顿占比异常，并与请求停顿在时间上相符；需正确处理累计计数和直方图。
- **容易混淆**：jvm_heap_stress、分配量上升、CPU 压力。堆紧张可能先触发 GC，不能把后续 GC 一律当成独立根因。
- **如何区分**：比较已有 GC 序列、堆变化和请求时间，核对先后及回收效果。没有 GC 观测时，不能仅凭“所有接口都慢”认定垃圾回收压力。

## Java 方法与数据库接口

JDBC 是 Java Database Connectivity（Java 数据库连接接口）。JDBC span 记录的是客户端调用范围，不一定等于数据库服务端执行时间。

### `jvm_method_exception` — Java 方法异常

- **中文含义**：Java 方法执行时发生异常，改变正常控制流程。
- **支持线索**：同一方法新出现异常类、栈位置或失败事件，并能对应本次请求失败。
- **容易混淆**：jvm_jdbc_exception、对下游失败的包装异常、正常业务校验。顶层方法打印异常不代表异常起源于该方法。
- **如何区分**：检查已有完整异常链、最初抛出位置、方法 span 和下游结果，比较正常窗口是否已有同类异常；不能仅凭 ERROR 等级判定。

### `jvm_jdbc_exception` — Java 数据库接口异常

- **中文含义**：Java 数据库客户端调用抛出异常，定位到 JDBC 调用路径。
- **支持线索**：异常链或调用事件明确指向数据库客户端操作，并与相关请求失败对应。
- **容易混淆**：数据库服务端故障、网络连接失败、连接池耗尽、合法约束冲突和普通方法异常。连接池校验失败也可能只是下游不可达的表现。
- **如何区分**：查看已有异常原因、数据库错误码/语句类型、连接池及数据库端观测；核对异常在连接、执行还是提交阶段。仅有 JDBC 报错不能排除网络或数据库才是故障源。

### `jvm_method_latency` — Java 方法执行延迟

- **中文含义**：某个 Java 方法的执行范围出现额外等待或处理延迟。
- **支持线索**：相同方法、可比请求的耗时增加，且已有子调用不足以解释增量；其他方法对照有助于定位。
- **容易混淆**：jvm_jdbc_latency、线程排队、锁等待、CPU/GC 压力和未记录的依赖调用。方法变慢不等于已查明方法内延迟的成因。
- **如何区分**：按同请求查看方法和子调用，正确处理并行区间；结合已有资源、线程及日志。父子记录不完整时，不把未记录时间全部认定为方法本身的故障。

### `jvm_jdbc_latency` — Java 数据库接口调用延迟

- **中文含义**：Java 数据库客户端调用出现额外延迟。
- **支持线索**：延迟集中在同类 JDBC 执行或提交操作，并与上层请求等待对应；若数据库端处理相对稳定，客户端路径解释更有依据。
- **容易混淆**：真实慢查询、数据库锁等待、连接池等待、网络延迟和 jvm_method_latency。仓库层方法名或 JDBC span 变慢，不能单独证明客户端被延迟。
- **如何区分**：比较已有客户端、数据库端、连接池和同类查询记录，分清借连接、执行、提交阶段。没有数据库端观测时保留归属疑问，不把数据库依赖自动算成应用自身根因。

### `jvm_method_mutated` — Java 方法返回结果或行为被改变

- **中文含义**：方法返回值或运行行为改变，造成与原有业务逻辑不一致的结果。
- **支持线索**：可比输入和依赖结果下，某方法的实际输出或后续分支异常，且已有记录能把差异定位到该方法。
- **容易混淆**：http_payload_modified、合法数据变化、缓存差异和方法异常。错误业务结果不自动意味着方法被修改。
- **如何区分**：对照授权记录中的输入、方法输出、依赖返回和最终 HTTP 结果。内部结果正常而传输后变化偏向 HTTP 路径；缺少输入/输出观测时不能反推具体返回值。

## 名称解析与时间

DNS 是 Domain Name System（域名系统），负责把名称解析为地址。

### `dns_resolution_failed` — 名称解析失败

- **中文含义**：无法取得目标名称可用的解析结果，连接可能尚未进入目标服务。
- **支持线索**：授权日志或调用事件明确记录域名不存在、解析超时或解析服务错误，且对应本次失败目标。
- **容易混淆**：目标停机、网络不可达、错误域名和 dns_resolution_wrong。泛化的“连接失败”不是 DNS 失败证据。
- **如何区分**：查看失败发生在解析还是连接阶段，核对实际查询名称与正常窗口同类请求；已有地址不意味着本次刚完成了解析，可能来自缓存。

### `dns_resolution_wrong` — 名称解析到错误目标

- **中文含义**：解析返回了地址，但该地址不是这次请求应访问的目标。
- **支持线索**：已有解析/连接记录表明请求去了错误目标，并有正常名称映射或服务身份记录作对照。
- **容易混淆**：合法负载均衡、地址轮换、陈旧缓存和应用配置错误。解析地址变化或证书报错都不能单独证明解析错误。
- **如何区分**：对照同一名称的解析结果、实际连接对端及其身份。只查到连接超时、没有地址证据时，不能区分错误解析与一般不可达。

### `clock_skew` — 系统或进程时钟偏移

- **中文含义**：某个进程或系统的时间相对其他组件发生偏移，可能影响时间判断、过期检查和跨服务事件顺序。
- **支持线索**：多个相关请求呈一致的跨组件时间偏移，或已有时间同步、令牌时间校验等记录与之对应。
- **容易混淆**：采集延迟、时区/单位错误、异步处理和埋点位置差异。负时间差、令牌过期或单个异常 span 都不能单独定类。
- **如何区分**：先统一单位和时区，区分事件时间与采集时间；比较多组相关请求及正常参照。某些时钟偏移不会改变记录的持续时间，不能要求一定出现负耗时。
